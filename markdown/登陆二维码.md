## 考虑的东西
1. 二维码类型：可能是微信、qq、github 等
2. 二维码图片服务端返回前端不同形式的处理
3. 二维码的状态变更如何处理（成功 / 失败 / 超时）
4. 登录态保存
5. 鉴权
6. 单点登陆



### 二维码的处理
在不同的平台上面会有相关 API 调用文档，参考官方文档即可。

图片在服务端向第三方申请后可能为三种类型：url、base64和二进制文件

#### 不同格式图片的处理
服务端返回是 url 的话直接放 `img`标签

```html
<img :src="url" />
```

如果是 base64 的话也可以用 `img`标签，但是需要告知浏览器类型

```html
<img :src="`data:image/jepg;base64,`"
```

关于其他文件格式的 base64 也可以指定类型来进行渲染

```latex
data:text/plain,文本数据

data:text/html,HTML代码

data:text/html;base64,base64编码的HTML代码

data:text/css,CSS代码

data:text/css;base64,base64编码的CSS代码

data:text/javascript,Javascript代码

data:text/javascript;base64,base64编码的Javascript代码

data:image/gif;base64,base64编码的gif图片数据

data:image/png;base64,base64编码的png图片数据

data:image/jpeg;base64,base64编码的jpeg图片数据

data:image/x-icon;base64,base64编码的icon图片数据
```

但对于二进制文件的话，就需要采用 blob + url 的形式创建

```javascript
URL.createObjectURL(new Blob([xxx], , { type: 'image/png' }));
```

还可以通过另外一种方式：canvas 进行绘制

```javascript
createImageBitmap(blob).then(bitmap => {
    ctx.drawImage(bitmap, 0, 0);
    bitmap.close();
});
```

### 如何知道用户扫码
![画板](http://oss.snailuu.cn/picgo/1741059883965-84ed1090-69ca-42ae-832e-7552148e2b03.jpeg)

这里有几种方式：http 短轮询、 sse 服务端推送以及 http 长轮询

针对于这个场景下， http 长轮询会是比较好的选择。

在一开始会建立连接，每次二维码状态更改的时候就会响应数据，接着再重新建立一个新的连接。

### 登录态的保存
服务端在接收用户扫码后会有一个回调函数返回同时会有身份信息，先将这个用户基本信息存储在一个过期时间比较长的 token 上，另外生成一个携带用户身份权限的短时间 token 一起返回。

### 单点登陆
> 单点登录（Single Sign-On，简称 SSO）是一种身份验证机制，允许用户只需登录一次，就可以使用同一组凭据（例如用户名和密码）访问多个关联但独立的系统或应用程序，而无需在每个系统上分别登录。
>

这时候就需要思考的一个问题就是：跨域身份信息如何存储？

#### 前端数据持久化方案
| 方案 | 跨域支持 | 访问速度 | 安全性 | 浏览器兼容性 | 同异步操作 | 数据结构支持 | 与服务器交互 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **LocalStorage** | 无（同源限制） | 快（同步） | 低（明文存储） | 高 | 同步 | 中（需序列化） | 无 |
| **SessionStorage** | 无（同源限制） | 快（同步） | 低（明文存储） | 高 | 同步 | 中（需序列化） | 无 |
| **Cookies** | 有（通过配置） | 中等（同步） | 中（可加密） | 高 | 同步 | 低（字符串） | 有（HTTP 自动发送） |
| **IndexedDB** | 无（同源限制） | 中等（异步） | 中（复杂管理） | 高 | 异步 | 高（结构化数据） | 无 |
| **Cache API** | 无（同源限制） | 快（异步） | 中（依赖 SW） | 中（需 SW） | 异步 | 中（资源缓存） | 有（可拦截请求） |
| **File System API** | 无（同源限制） | 中等（异步） | 中（用户授权） | 低（实验性） | 异步 | 高（文件系统） | 无 |
| **State Management** | 无（同源限制） | 快（内存为主） | 中（依赖存储） | 高 | 同步/异步 | 高（自定义） | 无 |


> **Cookies**：唯一天然支持跨域的方案，通过设置 domain 属性（如 .example.com）可以在子域间共享，或通过 SameSite 属性控制跨站行为。
>



因此对于单点登陆的场景，可以选择将身份信息存储在 cookies 上。

除此之外还可以利用 **浏览器指纹** 的唯一性，将 浏览器指纹与用户身份在服务端临时存储。
